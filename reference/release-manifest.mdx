A RampSpec release manifest binds the four repositories and their generated artifacts to one auditable product release. Consumers must not select components by branch name or by whichever build is newest.

<Warning>
  No tagged runtime release exists yet. The checked example is deliberately
  marked `unreleased`; its null versions and empty artifact lists must not be
  interpreted as a working compatibility set.
</Warning>

## Compatibility contract

| Component | Compatibility key                                            | Breaking change                                                                                    |
| --------- | ------------------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| Frontend  | Backend API major and consumed schema major.                 | Removing a supported backend major or changing a required response field.                          |
| Backend   | API major, schema major, runner protocol, and report format. | Removing or changing an operation, field, rule meaning, event, or canonical report representation. |
| Contracts | Contract major, spec hash, network, and deployment manifest. | Changing storage, method arguments, events, authorization, or commitment semantics.                |
| Docs      | Product version and imported artifact hashes.                | Publishing guidance or examples that require a different runtime compatibility set.                |

Additive API fields remain compatible when consumers ignore unknown fields. Removal, type changes, required-field additions, semantic changes, and altered contract interfaces require a new major version, migration notes, and a stated compatibility window.

## Required fields

The machine-readable schema is [`schemas/release-manifest.schema.json`](/schemas/release-manifest.schema.json). Each manifest records:

- schema version, product version, channel, and release timestamp;
- exactly one frontend, backend, contracts, and docs component record;
- repository, release status, immutable tag, full commit SHA, and artifacts;
- artifact kind, repository-relative path, and lowercase SHA-256 digest;
- compatible API, JSON Schema, and contract major versions;
- every breaking change and at least one migration note when a break exists;
- verification status, timestamp, and reproducible command.

An unavailable component must use null tag and commit values and an empty artifact list. A released component must provide all three. This prevents a planning document from resembling release evidence.

## Verification procedure

1. Obtain the manifest from the docs release rather than from an unreviewed branch.
2. Run `npm run lint:manifests -- path/to/manifest.json` to validate its semantic constraints.
3. Fetch each component by its immutable tag and confirm the full commit SHA.
4. Recompute SHA-256 for every listed artifact and compare the lowercase digest.
5. Confirm the frontend, API, schema, and contract majors match the manifest.
6. Read all breaking changes, migration notes, and compatibility-window dates before upgrading.
7. Verify network-specific deployment manifests and contract IDs through the named Stellar RPC endpoint.
8. Record the verification timestamp and command without changing the referenced release artifacts.

The repository keeps an executable [unreleased example](/examples/release-manifest.planned.json). It validates the future shape while honestly representing the current absence of runtime releases.

## Release sequence

The backend and contracts owners publish their tagged artifacts first. The frontend owner verifies its generated clients against those tags. The docs owner then imports hashes, validates the complete manifest, publishes migration guidance, and releases the matching documentation channel. See [repository ownership](/governance/repository-ownership) for review routing.
