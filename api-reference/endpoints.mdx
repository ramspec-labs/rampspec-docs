The API endpoint reference is generated from a tagged `rampspec-backend` OpenAPI artifact. Authored documentation explains how to consume that artifact but does not define endpoint paths or payload fields.

## Availability

The `v0.2.0` backend OpenAPI artifact is imported at `generated/openapi/openapi.json` with its source commit and SHA-256 in `generated/openapi/source.json`.

The executable reviewer surface is deliberately smaller than the control-plane design: `GET /health`, `GET /version`, `POST /v1/reference-runs`, and `GET /v1/reference-runs/{runId}` are implemented. Other control-plane operations in the document remain interface contracts for later runtime work and must not be presented as deployed.

## Import and integrity

The synchronization workflow downloads `openapi.json` from the named public backend release. It requires the backend release tag, verifies that tag's full commit SHA, and checks the expected SHA-256. The import rejects an invalid document or digest mismatch, preserves the released bytes, and records provenance in `generated/openapi/source.json`. CI then recomputes the digest so manual changes fail.

```powershell
npm run import:openapi -- `
  --source <openapi-path-or-url> `
  --tag <backend-tag> `
  --commit <40-character-commit> `
  --sha256 <64-character-digest>
```

The committed provenance file supplies these values for the imported release.

## Authentication

The reference-run operation is public but requires the synthetic `X-RampSpec-Organization` tenant header and an idempotency key. The broader control-plane design declares bearer authentication, but no hosted authentication service is claimed by this release. Examples must use synthetic identifiers and must not embed bearer tokens.

## Errors

Consumers must use the generated response schemas and documented status codes. They should preserve machine-readable error codes, correlation identifiers, and retry guidance while treating unknown fields as additive. Documentation must not turn a missing operation or undocumented response into a guessed contract.

## Pagination and idempotency

Cursor names, page limits, continuation behavior, and replay semantics come from operation parameters and schemas. Mutating requests use an idempotency mechanism only when the released operation declares it. Retries must preserve the original request body and follow the backend's documented conflict behavior.

## Server-sent events

If the released API defines an SSE operation, the generated reference is authoritative for event names and payload schemas. Clients must handle reconnects, duplicate event IDs, terminal events, and authorization expiry. The documentation will link each event to its generated JSON Schema after the backend publishes the bundle.
