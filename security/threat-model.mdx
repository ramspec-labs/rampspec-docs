RampSpec evaluates systems that process authentication, identity, payment, and ledger flows. Its main security objective is to produce trustworthy, minimally sensitive evidence without becoming an unauthorized scanner, credential broker, signing oracle, tenant escape path, or false certification service.

<Warning>
  This is the intended architecture threat model. Runtime controls have no
  tagged release, deployment evidence, penetration test, sandbox review, or
  contract audit. Entries marked **Planned** are requirements, not verified
  protections.
</Warning>

## Scope and assumptions

In scope are the frontend, public API, workflow/control plane, public and local runners, target services/callbacks, Horizon/RPC, secret and object stores, report KMS, Soroban evidence path, GitHub App, outgoing webhooks, build/release pipeline, and four repositories.

Operators and target owners may make mistakes or abuse legitimate access. Target responses, scenario submissions, callbacks, browser content, report uploads, GitHub events, dependency artifacts, network/DNS answers, and external provider data are untrusted. Cloud/KMS/identity providers are trusted only within pinned configuration and monitored contracts.

Out of scope as guarantees are target correctness beyond the tested scope/time, third-party availability, user endpoint security, recovered copies of public evidence, legal/regulatory compliance, and SDF certification. These are limitations, not reasons to omit defensive controls.

## Protected assets

- target authorization and ownership records;
- organization membership, roles, sessions, service identities, and audit history;
- target and runner secrets, Stellar seeds, wallet authorization, KMS and contract-admin keys;
- synthetic identity fixtures and any sensitive redacted evidence;
- canonical reports, signatures, suite locks, standards snapshots, artifacts, and baselines;
- workflow state, idempotency keys, leases, callback routes, schedules, and gate decisions;
- runner, build, release, schema, WASM, binding, image, and deployment provenance;
- availability, quotas, and the safety boundary that prevents unauthorized or active-pubnet work.

## Actors

Expected actors are Viewer, Auditor, Maintainer, Admin, Owner, CI service account, schedule identity, runner identity, report signer, evidence attestor, contract administrator, and platform operator. Adversaries include an anonymous internet user, compromised member/service account, malicious target, malicious contributor/scenario author, compromised runner/dependency/provider, cross-tenant attacker, webhook sender, and insider with partial privilege.

No single role should authorize target ownership, broaden execution policy, read a secret, execute a stateful run, publish evidence, and administer the contract.

## Trust boundaries

| ID  | Boundary                                   | Data crossing                                               | Required controls and failure behavior                                                                                                      |
| --- | ------------------------------------------ | ----------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| B01 | Browser to frontend                        | UI assets, session bootstrap, report views                  | CSP/security headers, dependency integrity, no secret storage, output encoding; deny sensitive rendering on auth uncertainty.               |
| B02 | Frontend to API                            | Authenticated commands and tenant reads                     | TLS, CSRF/origin checks, scoped auth, object authorization, schema/size/rate limits, audit; deny by default.                                |
| B03 | API to workflow                            | Immutable run intent, tenant/policy context                 | Signed/versioned command, idempotency, durable handoff, policy digest; ambiguous enqueue is reconciled, not repeated.                       |
| B04 | Control plane to public runner             | Leased scenario, capabilities, short-lived credentials      | Workload identity, signed image, isolated job, destination/value limits; no eligible runner means blocked/indeterminate.                    |
| B05 | Control plane to local runner              | Outbound pairing, lease, local secret handles               | Mutual identity, organization binding, allowlists, expiry/revoke; control plane cannot read local secret values.                            |
| B06 | Runner to target/callback                  | Protocol/browser requests, synthetic data, responses        | Verified ownership, DNS/IP/redirect controls, rate/value/mutation limits, parser limits, local redaction; unsafe destination stops.         |
| B07 | Runner to Horizon/RPC                      | Network queries, simulations, submissions                   | Pinned network/passphrase/endpoints, bounded responses, transaction reconciliation; outage is infrastructure-indeterminate.                 |
| B08 | Backend to secret/KMS/storage              | Wrapped credentials, signing operations, redacted artifacts | Workload identity, envelope keys, purpose scopes, access logs, retention/object integrity; no fallback to plaintext/local logs.             |
| B09 | Evidence worker to Soroban                 | Compact hashes, simulation, signed transaction, events      | Verified manifest/code hash, attestor policy, preview/approval, idempotent reconciliation; mismatch blocks submission/claim.                |
| B10 | Platform to GitHub                         | Signed events, installation tokens, checks                  | Exact-body signature validation, minimum App permissions, immutable mapping, fork isolation; ambiguous event cannot start privileged work.  |
| B11 | Platform to webhook/notification recipient | Signed redacted events and expiring links                   | SSRF controls, signing/replay defense, bounded retry, recipient scope; delivery failure cannot change report truth.                         |
| B12 | Build/release to deployment                | Images, packages, schemas, WASM, manifests                  | Protected review, locked dependencies, provenance/SBOM, signatures, digest pinning, reproducibility; unverifiable artifact is not promoted. |

Encryption authenticates neither the target nor tenant intent by itself. Every boundary also needs authorization, validation, limits, observability, and an explicit non-success state.

## Authorization and confused-deputy rules

Every action evaluates authenticated subject, organization, object, operation, target ownership, network, mode, suite/policy version, runner capabilities, credential purpose, value/destination limits, and approval state. Resource IDs from URLs, events, scenarios, reports, or GitHub payloads are never sufficient authority.

Background jobs carry signed immutable tenant/action context and reauthorize at irreversible boundaries. A service that can read a queue cannot broaden a destination or retrieve a secret. A local runner cannot claim another organization. A report signer cannot choose report content. An evidence publisher cannot use contract administration to bypass attestor policy.

## Data-flow rules

Collect the minimum synthetic/request metadata at the runner. Redact before crossing the runner boundary, classify artifacts before upload, encrypt in transit/at rest, scope every object to tenant/run, and expire it by policy. Secrets never enter scenario files, canonical reports, URLs, events, telemetry, support bundles, or on-chain state.

Prohibited data triggers stop, quarantine, access restriction, owner/privacy notification, deletion or hold decision, and validation that downstream caches/exports/notifications were handled. Hashes of sensitive low-entropy values can still leak and are not automatically safe.

## Availability and integrity behavior

Dependency or infrastructure failure is distinct from target nonconformance. Unknown side effects are reconciled before retry. Missing required evidence, cleanup failure, signature failure, stream gap, or unavailable runner/dependency yields blocked or indeterminate, never pass. Kill switches stop new risky submissions while preserving report access, cleanup, revocation, and incident evidence where safe.

## Security validation matrix

| Evidence                  | Required scope                                                                                     | Current status                            |
| ------------------------- | -------------------------------------------------------------------------------------------------- | ----------------------------------------- |
| Unit/property/fuzz tests  | Parsers, policy, auth, IDs, canonicalization, contract transitions                                 | Planned in owning repositories            |
| Cross-tenant integration  | Every API/repository/cache/job/object/event mutation and read                                      | Planned backend gate                      |
| Network/sandbox tests     | SSRF/rebinding/redirects, egress, job escape/residue, credential isolation                         | Planned runner gate                       |
| End-to-end abuse journeys | Unauthorized target, fork trigger, malicious target/scenario, duplicate side effect, pubnet denial | Planned release fixtures                  |
| Cryptographic vectors     | Report/webhook signatures, rotation/revocation, artifact and contract hashes                       | Planned SDK/backend/contracts gate        |
| Independent review        | Architecture threat model, web/API penetration test, runner sandbox, Soroban audit                 | Required before production; not completed |
| Operational exercises     | Secret/PII incident, key compromise, abuse stop, backup/region restore, dependency/GitHub outage   | Required before production; not completed |

An independent reviewer must map each `T` entry to a test ID, control owner, deployed configuration evidence, residual risk decision, and dated verification. A missing mapping is a tracked release gap, not an implicit acceptance.

## Residual risks and review triggers

Even with controls, authorized tests can affect target rate limits/state, synthetic transactions can have cost, compromised operators/providers can abuse access, public commitments leak activity timing, and externally downloaded evidence cannot be recalled. Owners accept bounded residual risk per target/network/run; platform-wide exceptions require security review and expiry.

Review this model for a new trust boundary, protocol/mode/network, secret/signing path, data class, runner model, integration, contract/schema major, cloud/provider/region, incident, material dependency, or control failure, and at least annually after production. Changes update threat IDs, tests, runbooks, and compatibility/release notes together.

Use the private process in [Security Policy](/SECURITY) for vulnerabilities. Do not test suspected weaknesses against systems or data you do not own.
